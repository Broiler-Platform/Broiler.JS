The first run (`first-run/`, at `3e37c44`, 19:22:54Z to 20:02:35Z) left 1,062 differences unclassified
and put 2 × 1,104 in class (a) that were not arm J's errors:

- **A defect of S (class (c)).** `ExactRounding.ApplyUnsignedRoundingMode` answered a value exactly at
  the window's upper end with the lower end under the "zero" mode. The clause asserts
  r1 < x < r2 once x = r1 is answered, and both engines' NudgeToCalendarUnit answer a progress of 1 with
  r2 before calling. Arm J's variants repeat that line, so they answered the upper end, and the
  classifier, which applied the clause without its callers, called them wrong. S's precondition
  admitted the upper end, so an exact end is now itself under every mode (`45e4db8`, with a unit test);
  arm V's window variant now repeats its caller's line too, and arm V's one-step variant is called
  where its engine calls it, below the upper end.
- **A defect of the comparison.** Arm V's `TryParseStringInteger` reports a text too wide for its
  ceiling as `true` with no value and the value's sign; the entry point dereferenced the missing value
  and threw, on 1,062 texts of the values around 2^20 bits. The entry point now reads the member's
  contract.
- **The classifier** answers an exact upper end with r2, as the clause's callers do, and words one
  reason more exactly ("misses the clause's special case" wherever the reference is exact). No other
  class it gives changed: every other group of the first run has the same count in this one.

## 7. The negative controls

`negative-control/arm-v.patch` made arm V's `JsBigInt.Add` charge one unit more for B1P's first pair,
2^3277 + 1 and 2^4021 − 1. `negative-control/arm-j.patch` made arm J's `JSValue.IntValue` answer one
