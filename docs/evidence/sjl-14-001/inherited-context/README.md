# The inherited-context probes (SJL-14.1, task 1.1; decision D44)

**Written:** 2026-11-03, at milestone SJL-14 (work package SJL-14.1) of the shared JavaScript libraries programme, with
this bundle's rule, before any code it judges exists. **What they are for:** decision D44 has the bridge pass the
inherited context of eval code and the dynamic function's goals in the library's request, and pass the visible private
names "only where task 1.1's probes find that Broiler.JS checks them at parse time today". These probes record, for
each context the decision names, what each engine answers today, so that the bridge's merge (W1) and the side-by-side
run (rule part C) meet each difference with a row. Nothing here is a verdict, and nothing here is a run of the shared
library.

## What was run

- **The probes**: direct `eval` inside global code, functions (called and constructed), arrows, object methods and
  getters, class methods and static methods, base and derived constructors (and an arrow in one), instance and static
  field initialisers (and an arrow in one), class static blocks and a class element's computed key, in strict and
  sloppy callers, of seven texts: `new.target`, a super property, a super call, `arguments`, a declared and an
  undeclared private name, and a strict reserved word; then nested and indirect eval, positions (row N25), a hashbang
  (N26), a field named `static` (R36), the strict literals (K1); and `Function`, `GeneratorFunction` and
  `AsyncFunction` with bad parameters and bodies (P26, D61). [`probes.tsv`](probes.tsv) lists every probe with the
  specification's answer (ES2026 PerformEval, 19.2.1.1, and CreateDynamicFunction, 20.2.1.1.1) and why.
- **Two forms**: the direct form, [`ic-values.js`](ic-values.js), writes each probe's context in the program itself;
  the in-eval form, [`ic-values-in-eval.js`](ic-values-in-eval.js), compiles each context by an indirect eval, so that
  the functions and classes holding the direct eval are themselves eval code. Both are generated by
  [`gen_probes.py`](gen_probes.py) and run as `prelude.js` + the form + `epilogue.js`.
- **Both engines**, each built from a clean `git archive` of its default branch in a scratch folder, never in a
  checkout ([`build.txt`](build.txt)): Broiler.JS `33d3093b` through its shell `BroilerJS --script-host`, Broiler.VM
  `c5bde2b` through its conformance root's `--test262` mode, by [`run_probes.sh`](run_probes.sh) under `TZ=UTC` with
  no `LANG`, `LC_*` or `BROILER_*` variable. Each run's program, transcript and answers are under `runs/`;
  [`answers.tsv`](answers.tsv), written by [`merge_answers.py`](merge_answers.py), holds every probe's answer in each
  engine and form beside the specification's, and its column `matches` marks each (`=` the specification's answer,
  `x` another), in the order Broiler.JS direct, Broiler.JS in eval, Broiler.VM direct, Broiler.VM in eval. A refusal is
  matched on its error name: each engine's message is its own, and Broiler.VM's eval refusal reads "the evaluated
  source is not a program this profile admits" for every row.
- [`hashes.txt`](hashes.txt) gives the SHA-256 of every file here.

## What the answers say

**Broiler.VM answers as the specification does** in every probe of both forms, but two: a class element's computed
key evaluates its eval as sloppy code (IC154, where class code is strict), and the dynamic function's parameters are
not parsed alone (Y06, Y07: P26's Broiler.VM half, hand-off H18).

**Broiler.JS answers as the specification does in the direct form** for every flag the request carries, but where
these rows say otherwise. Each is a correction of Broiler.JS that the library makes once the bridge passes the
context, listed in [`../corrections.md`](../corrections.md) under K10 (rows IC1 to IC7, beside the correspondence's
R24, N25, N26 and R36):

| Row | What Broiler.JS answers today | Probes | The specification |
|---|---|---|---|
| R24 | `eval('super()')` in a base class's constructor is admitted at the parse and throws `TypeError` | IC94 | an early SyntaxError: the constructor is not derived |
| IC6 | `eval('super()')` in a derived class's constructor, after its own `super()`, in a class with fields, is refused at the parse | IC101, IC108 | admitted; `ReferenceError` when it runs (super called twice) |
| IC2 | eval in an instance, derived or static field initialiser, or in an arrow in one, is sloppy | IC119, IC126, IC133, IC140 | strict: class code is strict |
| IC7 | eval in a class element's computed key is sloppy (Broiler.VM's answer too) | IC154 | strict |
| IC3 | `new.target` in an arrow in a field initialiser is the constructor | IC127 | `undefined` |
| IC4 | a static field initialiser's and a computed key's eval do not see the class's private names | IC138, IC152 | visible |
| IC5 | a computed key's eval does not see the enclosing function's `arguments` | IC151 | the function's `arguments` |
| N26 | a hashbang at the start of a strict caller's eval text is refused | X05 | admitted (eval code is a Script) |
| R36 | a strict caller's eval refuses a class field named `static` | X07 | admitted |
| T16 (K1) | a strict caller's eval admits `08` | X09 | refused |
| P26, D61 | `Function('a', '}); (function(){')` is admitted | Y07 | refused (the body is parsed alone) |

**In the in-eval form Broiler.JS loses the function context** (row IC1): every direct eval of `new.target` in a
function that is itself eval code is refused (each `*-NT` probe but global code's, and X01, X12), and `Function`
called from eval code admits a super property in its parameters or body (Y02, Y09) and fails with an
`ArgumentNullException` for a super call in its body (Y08). Broiler.VM answers both forms alike.

**What D44 reads from them.**
- **Strictness, the function, method, derived-constructor and field-initialiser flags**: Broiler.JS's direct-eval
  support computes each today, and the bridge passes each (the derived-constructor flag from the class's heritage,
  row R24; strictness also for a field initialiser and a computed key, rows IC2 and IC7). A static block's eval sets the
  function and method flags (F22); the probes agree with both engines' answers there (IC141 to IC147, X11).
- **The visible private names**: Broiler.JS checks them at the parse of eval code today (`DirectEvalSupport.Validate`
  is given the names in scope: the PU probes are refused "Private name is not declared in an enclosing class", and the
  PD probes are admitted in every class context but IC4's). So, by decision D44's own condition, **the bridge passes the
  visible private names in the request at W1**, the set the library checks; IC4's two contexts are corrections.
- **The caller's lexical names** stay absent (decision D16, finding F21); no probe here reads them.
- **The dynamic function's goals**: Broiler.JS parses the assembled source, so a body that closes the function early is
  admitted (Y07); the library parses parameters and body under their own goals once the bridge passes them (P26, K10).
- **Messages and positions** (decision D46): each engine's message text is recorded in `answers.tsv` and the
  transcripts, positions included where Broiler.JS gives them (X03, X04: "Unexpected token EOF: at 0, 0", row N11),
  for the generated message table of rule part C's class M.
