**Where they differ:**

- **`FromHex`, arm J (11,036, row B1).** `setFromHex` parses its whole input before it honours the
  destination's length, so a character past the bytes that fit, which the specification never reads,
  raises `SyntaxError`.
- **`GetSubstitution`, arm J's `JSRegExp.Replace(string, string)` (43,548, row S3).** The third template
  walk, which `replace` reaches when a RegExp's `Symbol.replace` is absent, never substitutes `$<name>`.
- **`JSON parse`, arm J (25,345).** Documents nested past System.Text.Json's depth of 64 are refused
  (J1, 19,201), an escaped lone surrogate is refused (J2, 4,096), and a raw one lets the .NET
  `ArgumentException` of the transcoding escape (J3, 2,048).
- **`StringPad`, arm V (84, row P2).** Past this family's string ceiling, an empty filler is refused with
  `RangeError` before any unit is charged, where StringPad returns the String and S charges the early
  answer's units, max(1, length), as JSD-0070 decision 3 sets them. On those inputs the value differs, so
  the charge is the outcome's and is not compared on its own.

No other variant differs. In particular arm J's `JSON.parse` answers `1e400` with `Infinity` here too,
as corpus revision 12's vectors found, so row J4 does not appear.

**What no arm runs** (`summary.json`, `notImplemented`): TrimString, which both engines already take from
the library (S runs over its population alone); `AdvanceStringIndex` below index 0, `CodePointAt` beyond
the String, the relative index for lengths above `int.MaxValue`, arm V's JSON validation at 64 and arm J's
at any limit, and both String-pattern template walks with captures or named groups, each for the reason
the revision gives; and arm J's pad to more than 2^24 + 1 code units. *Corrected 2026-10-14:* the
revision's section 2 says of that last bound that "correspondence row P4 says what it does there, and
the vectors show it". The vectors do not: corpus revision 12 pads to 2^24 + 1 code units at most, so P4
rests on the correspondence's reading alone. The bound stands on its arithmetic, since .NET cannot hold
the Strings it would build.

## 4. The class (b) differences and their vectors

None. The comparison calls S under each arm's own policy: Broiler.VM's string ceiling of 2^24 and JSON
depths of 512 and 1024 against arm V, and no limit the population reaches against arm J. So a refusal at
an arm's own limit is S's too and is not a difference.

## 5. The first run, and what changed before this one

The first run (`first-run/`, at `7af1424`, 18:05:18Z to 18:27:12Z) gave the same 80,013 differences,
byte for byte (section 8). The classifier as committed at `7af1424` put 63,628 in class (a), 3,158 in
class (c) and left 13,227 unclassified:

- **A defect of the classifier, not of S.** The comparison writes a field longer than 4,096 characters as
  `len:<length>:sha256:<digest>`, its UTF-16 length and the SHA-256 of its UTF-8 text. The classifier read
  such an input as no input ("the input was shortened in the listing", 13,227), and compared such a result
  of S with the reference's full text, which never matched ("S is not the reference's", 3,158). All
  16,385 are `JSON parse` documents of class J1R, which arm J refuses past its depth.
- **The check.** For J1R lines 0, 4 and 16, S's shortened result has the length and digest of the
  reference's full result, and the shortened inputs have the length and digest of the population's lines.
- **The correction (`95f4387`).** A shortened input is read from the population at its line, and only
  when its length and digest are the listed ones; a shortened result is compared with the reference
  shortened the same way. Nothing else changed. Applied to the first run's listing, it gives this run's
  classes, every one of them.

The rule asks for the whole comparison again after a class (c) difference, and this run is that, under the
corrected classifier, committed before it ran.

## 7. The negative controls

`compare-text --controls` runs the rule's two copies alone (`negative-control/`), from the comparison
commit: arm V's `GlobalUriEncode` charging one unit more for U1C's `"A"`, and arm J's `DecodeBase64`
with the first byte changed for B1E's `"AAAA"` in the standard alphabet, loose, unbounded. Each is
reported as one difference, at exactly that input (`negative-control/differences.tsv`):

- arm V's on U1C line 65 (`A`): `str:A|charge:1` from S, `str:A|charge:2` from the copy;
- arm J's on B1E line 2955 (`AAAA`, `base64/loose/unbounded`): `read:4|bytes:000000|ok` from S,
  `read:4|bytes:ff0000|ok` from the copy.

The classifier leaves both unclassified: the first for its charge alone, the second because the copy's
operation is not one the reference answers. The copies were in `TextArms.NegativeControls`, which the
judged comparison never calls. As the rule asks, they were then removed, with the `--controls` option, in
the change that adds this bundle; [`negative-control/controls.patch`](negative-control/controls.patch),
applied with `git apply`, restores them.
